# 03. 구현

빈 구현마다 **입력 · 출력 · 확인 방법**을 정리했습니다.
순서대로 읽을 필요는 없습니다. 구현 중인 클래스를 찾아 읽으면 됩니다.

각 클래스의 Javadoc 에 더 자세한 명세가 있습니다. 이 문서에 없는 내용은 Javadoc 에서 확인하세요.

> **강의 순서:** `ArticleBodyExtractor` → `CommentModerator` → `HarmfulPhraseDetector` →
> `IssueAnalyzer` → `ArticleChunker` → `EmbeddingIndexer` → `StoryProcessor` →
> `BodyVectorPlan` · `SummaryVectorPlan` → `SearchService` → `RelevanceJudge` → `RelevancePostProcessor` →
> `AnswerGenerator` → `ChatService` (1단계) → `IssueTools` → `TopicSummarizer` → `ChatService` (2단계)

**기본 확인 도구**

```bash
./gradlew test                                              # 계약과 계층
./gradlew playground --tests '*<클래스>CheckTest'            # 빈 구현 하나의 확인
./gradlew bootRun                                           # 화면
docker compose exec db psql -U hn -d hnanalyzer -c "..."    # DB
```

**확인 테스트**는 빈 구현마다 하나씩 있습니다. 화면으로 확인할 수 있게 되기 전에도
구현 직후 바로 결과를 볼 수 있습니다. 빈 구현 상태에서는 `UnsupportedOperationException` 으로
실패하고, 구현하면 결과를 출력하며 통과합니다.

검색과 도구의 확인 테스트는 **적재된 데이터가 필요합니다.** 데이터 셋업을 실행하기 전에는
실패하지 않고 건너뜁니다(SKIPPED).

## 오케스트레이션

### StoryProcessor: 스토리 하나의 2~8단계

| | |
| --- | --- |
| **역할** | 스토리 하나를 중복 확인부터 적재까지 순서대로 처리하고 저장 |
| **입력** | `storyId`, 단계 통과를 알리는 `StageTracker` |
| **출력** | `COMPLETED` · `EXCLUDED` · `SKIPPED` |
| **확인 방법** | 데이터 셋업 탭에서 작은 건수로 실행 → 단계 체크와 제외 사유, `psql` 로 `story` · `article` · `analysis` 행 수. 재실행 시 처리한 스토리의 건너뜀 여부 |

실행 스레드, 진행 상황 계산, 로그 발행은 완성본 `PipelineSetupService` 가 맡습니다.

**셋업 파이프라인 8단계**

1. 수집 (완성본 뼈대가 수행)
2. 중복 확인
3. 댓글 검열
4. 기계적 정제
5. 본문 추출
6. 분석
7. 청킹
8. 적재

단계의 흐름과 단계별 완성본 · 빈 구현 구분은 [02. 전체 구조의 「흐름 1: 셋업 파이프라인」](02-전체-구조.md#흐름-1-셋업-파이프라인)
절에 있습니다. 구현 전에 먼저 확인하세요. 단계마다 호출할 부품과 규칙은 `StoryProcessor` Javadoc 에 순서대로 있습니다.

**주의 사항**

- 2단계 중복 확인은 댓글을 받아오기 **전**에 수행해야 의미가 있습니다
- 제외할 때도 `article` 행을 저장하세요. 그 행이 다음 실행의 중복 확인 기준입니다
- 단계를 통과할 때마다 `tracker.passed(단계)` 를 호출해야 화면의 단계 표시가 움직입니다
- 4단계 판정은 완성본 `PipelinePolicy.check` 를 쓰세요. 제외 여부와 저장할 정제 텍스트(절단 후)를 함께 돌려줍니다
- 댓글 수 · 치환 문자열도 `PipelinePolicy` 에 있습니다

### ChatService: Q&A 답변 스트리밍

| | |
| --- | --- |
| **역할** | 모델을 호출하고 답을 스트리밍. 세션 5 에서 1단계, 세션 6 에서 2단계로 채움 |
| **입력** | `conversationId` · 질문 |
| **출력** | `ChatEvent` 스트림: `plans` → `evidence` → `token` → `done` (검색이 없는 질문은 `token` → `done`) |
| **확인 방법** | Q&A 탭에서 질문 후 사이드바 계획 · 근거 카드 · 답변의 순차 표시 |

**1단계 (세션 5) — 질문마다 검색하는 RAG.** `RetrievalAugmentationAdvisor` 에 `SearchService` ·
`RelevancePostProcessor` · `ContextualQueryAugmenter` 를 넘겨 붙이고, 답변 규칙을 system 으로 넣어
호출합니다. Advisor 가 모델 호출 앞에서 검색 · 판단 · 질문 보강을 합니다.
응답 흐름은 `stream().chatClientResponse()` 로 받아 완성본 `ChatTurn.streamWithEvidence` 에 넘깁니다.
대화 기억은 아직 없습니다.

**2단계 (세션 6) — 도구와 기억을 쓰는 에이전트.** Advisor 를 빼고 `IssueTools` 를 도구로,
기억 Advisor 를 붙입니다. 검색은 모델이 `searchIssues` 를 골랐을 때만 일어나고, 답은 도구를 호출한
모델이 한 번에 생성합니다. 도구 안에서 만든 사건은 완성본 `ChatTurn` 이 전달합니다.

**주의 사항**

- 적재된 스토리가 0건일 때 안내 문구만 내보내는 분기를 빠뜨리면 빈 화면이 됩니다
- 1단계에서 `stream().content()` 로 받으면 Advisor 가 남긴 근거를 꺼낼 수 없어 근거 카드가 나오지 않습니다
- 2단계에서 `conversationId` 를 넘기지 않으면 예외가 발생합니다. 기본값이 없습니다
- 같은 `conversationId` 를 기억 Advisor 파라미터와 `toolContext` 에 **각각** 넣습니다. 서로 다른 통로입니다
- 질문 원문도 `toolContext` 에 넣습니다(`SearchContext.USER_QUESTION`). 계획 1 이 원문에서 키워드를 찾습니다
- 도구가 `ToolContext` 를 받으면 **모든** 호출이 그것을 채워야 합니다. 하나라도 빠지면 모델을 호출하기도 전에 예외가 발생합니다

## ai/: LLM 호출

### CommentModerator: 3단계 검열 판정

| | |
| --- | --- |
| **역할** | 댓글 하나의 카테고리별 점수와 검열 여부 판정 |
| **입력** | 댓글 텍스트 |
| **출력** | `ModerationVerdict` |
| **확인 방법** | `./gradlew playground --tests '*CommentModeratorCheckTest'` |

**주의 사항**

- `isFlagged()` 를 그대로 쓰면 안 됩니다. 설정에 적힌 카테고리의 점수만 임계값과 비교하세요
- `harassment` 계열은 의도적으로 목록에서 뺐습니다. 넣으면 기술 커뮤니티의 제품 비판이 대량으로 걸립니다
- 실제 수집 데이터에서 걸리는 댓글이 0건인 것도 정상입니다. 테스트가 그것도 확인합니다
- **설정에 적힌 카테고리가 응답 점수에 없을 수 있습니다.** 카테고리 목록은 `application.yml` 에서 바꿀 수 있고,
  모델이 채우지 않는 이름을 넣으면 점수를 못 찾습니다. 없는 값을 그대로 비교하면 실패합니다

### HarmfulPhraseDetector: 3단계 마스킹 구간

| | |
| --- | --- |
| **역할** | 검열에 걸린 댓글에서 **치환 대상 구간만** 추출 |
| **입력** | 댓글 텍스트 |
| **출력** | `MaskingResult`: 유해 구간 목록 |
| **확인 방법** | `./gradlew playground --tests '*HarmfulPhraseDetectorCheckTest'` |

**주의 사항**

- 모델에 원문을 다시 쓰게 하면 내용이 변조됩니다. 구간만 받아 애플리케이션이 치환합니다
- 원문에 없는 문자열을 돌려주면 치환이 되지 않습니다
- **유해 구간이 없으면 빈 목록입니다.** 구조화 출력은 모델이 필드를 빼면 `null` 을 줍니다.
  부르는 쪽이 목록을 바로 순회하므로 `null` 을 그대로 넘기면 안 됩니다

### ArticleBodyExtractor: 5단계 본문 추출

| | |
| --- | --- |
| **역할** | 태그를 제거한 텍스트에서 본문만 추출 |
| **입력** | 스토리 제목 + 정제 텍스트 |
| **출력** | 본문. 찾지 못하면 빈 값 |
| **확인 방법** | `./gradlew playground --tests '*ArticleBodyExtractorCheckTest'` |

**주의 사항**

- 제목을 같이 넘기지 않으면 어디가 본문인지 판단할 기준이 없습니다
- 찾지 못했을 때 빈 값을 돌려줘야 파이프라인이 제외 처리를 합니다. 본문이 아닌 텍스트를 억지로 돌려주면 그대로 저장됩니다

### IssueAnalyzer: 6단계 분석

| | |
| --- | --- |
| **역할** | 제목 · 본문 · 최상위 댓글 기반 구조화 분석 결과 생성 |
| **입력** | 제목 · `article.body` (5단계 산물) · 최상위 댓글 |
| **출력** | `IssueAnalysis` (`AnalysisMapper.toEntity(storyId, 분석)` 이 `analysis` 행으로 변환) |
| **확인 방법** | `./gradlew playground --tests '*IssueAnalyzerCheckTest'`. 셋업 후에는 **주제 탐색 탭 잠금 해제** |

**주의 사항**

- `techField` · `category` 의 값 목록을 프롬프트에 넣지 않으면 모델이 목록에 없는 값을 만들어냅니다
- **`keywords` 는 6개에서 10개를 지시하세요.** 검색 계획 1(`KeywordArrayPlan`)이 사용자 질문 안에 이 배열의
  키워드가 들어 있는지 보므로, 적게 뽑으면 그 계획이 0건 나는 빈도가 올라갑니다
- 구조화 출력은 값이 없는 문자열 필드에 `null` 이 아니라 **빈 문자열**을 줍니다.
  `analysis` 에는 적합 여부와 사유를 묶는 제약이 있어 그대로 저장하면 INSERT 가 실패합니다
  (`AnalysisMapper` 가 정규화해 주지만, 직접 엔티티를 만들면 이 제약에 걸립니다)
- 부적합 판정도 분석과 동시에 나옵니다. 별도 호출을 만들 필요가 없습니다
- `IssueAnalysis` 에는 `storyId` 가 없습니다. 모델이 알 수 없는 값이라 스키마에서 뺐고, 저장할 때 붙입니다
- 서술 필드(`summary` · `communityReaction` · `practicalImplication` · `unsuitableReason`)는 **한국어로** 쓰게 하세요.
  지시하지 않으면 원문 언어를 따라가 스토리마다 언어가 섞입니다. `keywords` 의 고유명사 · 제품명은 원문 표기 그대로 둡니다

### ArticleChunker: 7단계 청킹

| | |
| --- | --- |
| **역할** | 본문을 문단 단위로 분할 |
| **입력** | `article.body` |
| **출력** | 청크 목록 → `body_chunk` |
| **확인 방법** | `./gradlew playground --tests '*ArticleChunkerCheckTest'` |

**주의 사항**

- 돌려준 순서가 그대로 `seq` 가 됩니다. 흐트러지면 앞뒤 청크를 이어 붙일 때 어긋납니다
- 문단 경계를 찾지 못하거나 한 문단이 너무 길면 하드 리밋(2,000자)으로 자릅니다

### EmbeddingIndexer: 8단계 적재

| | |
| --- | --- |
| **역할** | 요약과 청크를 임베딩해 두 벡터 스토어에 적재 |
| **입력** | `storyId` · `IssueAnalysis` · 청크 목록 (두 메서드 모두 분석 결과를 받음) |
| **출력** | `summary_vector_store` · `body_vector_store` 행 |
| **확인 방법** | `./gradlew playground --tests '*EmbeddingIndexerCheckTest'` |

**주의 사항**

- 벡터 스토어 빈이 둘이라 **타입만으로는 주입되지 않습니다.** 생성자에서 두 빈을 이미 구분해 주입합니다
- **`Document` 의 id 는 UUID 문자열이어야 합니다.** `PgVectorStore` 가 `UUID.fromString` 으로
  파싱하므로 `storyId` 나 `"49588988-0"` 같은 값을 주면 `UUID string too large` 예외가 발생합니다.
  스토리와의 연결은 id 가 아니라 메타데이터의 `storyId` 로 합니다
- 메타데이터는 두 스토어 모두 `storyId` · `suitable` · `techField` · `category`, 본문 스토어는 `chunkSeq` 도 넣습니다.
  필터 값이 빠지면 검색 계획의 필터에 걸리지 않아 결과가 0건이 됩니다
- 재실행 시 같은 내용이 중복 적재되지 않는지 보세요. `storyId` 와 `chunkSeq` 로 식별합니다

### RelevanceJudge: 적합성 판단

| | |
| --- | --- |
| **역할** | 검색 후보 중 질문에 실제로 답이 되는 스토리 선별과 근거 대목 추출 |
| **입력** | 질문 + 후보별 제목 · 요약 · 원문 앞 2,000자 |
| **출력** | `RelevantStory` 목록: `storyId` 와 대목 (최대 5, 최소 1, 순서가 곧 근거 순서) |
| **확인 방법** | `./gradlew playground --tests '*RelevanceJudgeCheckTest'` |

**주의 사항**

- 후보가 적더라도 전부 버리면 답할 근거가 없어집니다. 최소 1건은 남기세요
- 모델이 목록에 없는 `storyId` 를 만들어낼 수 있습니다. 받은 것만 쓰는지 확인하세요
- 대목은 **원문에 그대로 있는 문장**이어야 합니다. 바꿔 쓴 대목은 완성본이 버립니다. 결과를 여러 필드로 받으므로 구조화 출력을 씁니다
- 대목은 번역하지 않습니다. 원문이 영어면 대목도 영어입니다

### RelevancePostProcessor: 근거 후처리

| | |
| --- | --- |
| **역할** | Spring AI `DocumentPostProcessor`. 검색 후보를 `RelevanceJudge` 로 걸러 근거 카드 내용을 채운 `Document` 로 돌려줌 |
| **입력** | `Query` (질문은 `query.text()`) + `SearchService` 가 찾은 후보 `Document` 목록 |
| **출력** | 근거 `Document` 목록 (판단 순서 = 근거 카드 순서) |
| **확인 방법** | `./gradlew playground --tests '*RelevancePostProcessorCheckTest'` |

세션 5 에서는 `RetrievalAugmentationAdvisor` 가, 세션 6 에서는 `searchIssues` 가 부릅니다.
판단 입력 만들기와 근거 `Document` 조립은 완성본 `EvidenceDocuments` 가 맡습니다.

**주의 사항**

- 후보가 0건이면 판단을 부르지 말고 빈 목록을 돌려주세요. 모델 호출 비용만 듭니다
- 원문 앞부분이 없는 후보는 판단 입력에서 빠집니다. `EvidenceDocuments.targets` 가 거릅니다

**주의 사항**

- 개별 스토리를 나열하는 답이 나오면 목적과 다릅니다. 흐름을 묶는 요약이어야 합니다
- 요약은 한국어로 나오게 프롬프트에 적으세요

- 근거에 없는 내용을 지어내지 않게 하는 것이 규칙의 핵심입니다
- 원문 타입(`category`)에 따라 서술을 구분하게 하세요. 공식 발표와 개인 의견을 같은 강도로 쓰면 안 됩니다
- 세션 5 에서는 세션 5 규칙만 씁니다. 필터 해석과 기억 기록 형식에 관한 규칙은 세션 6 에서
  `ChatService` 를 2단계로 바꿀 때 더합니다. 두 규칙 목록은 `AnswerGenerator` Javadoc 에 있습니다

## search/: 검색

### SearchService: 계획 실행과 병합

| | |
| --- | --- |
| **역할** | Spring AI `DocumentRetriever`. 네 계획 전부 실행, 중복 제거 후 후보 생성 |
| **입력** | `Query`: 검색어 + 검색 컨텍스트(원문 · 분야 · 원문 타입, `SearchContext`) |
| **출력** | 후보 `Document` 목록 (`Candidate.toDocument`). 계획별 히트 수와 실행 조건은 `query` 의 컨텍스트에 기록 |
| **확인 방법** | `./gradlew playground --tests '*SearchServiceCheckTest'` |

**주의 사항**

- **점수를 합치지 않습니다.** 척도가 서로 달라 비교 자체가 성립하지 않습니다
- 계획 3 은 청크 단위라 스토리 단위로 묶은 뒤 합쳐야 중복이 제대로 제거됩니다
- 계획이 돌려주는 것은 `storyId` 와 점수, 실행 조건입니다. 제목·요약은 주입된 색인 조회로 채웁니다
- 계획별 요약을 `SearchContext.record` 로 기록하지 않으면 화면 사이드바의 검색 계획이 비어 나옵니다.
  `DocumentRetriever` 는 `Document` 목록만 돌려주므로 이 값을 실어 보낼 곳이 컨텍스트뿐입니다

### KeywordArrayPlan · FullTextPlan: 계획 1 · 2 (완성본)

키워드 일치와 전문 검색은 Spring AI 를 쓰지 않는 SQL 조회라 **완성본으로 제공합니다.**
`SearchService` 는 네 계획을 모두 수행하므로 그대로 사용하면 됩니다.
결과와 실행 조건을 함께 돌려주는 형태는 계획 3 · 4 를 구현할 때 참고하세요.

- 계획 1 은 모델이 다듬은 검색어가 아니라 **사용자 원문**에서, 저장된 키워드가 들어 있는지 찾습니다.
  두 단어 이상인 키워드(`digital sovereignty`)도 찾고, 대소문자는 가리지 않고, 「VMware의」처럼 붙은 조사도 경계로 봅니다
- 계획 2 는 파싱에 실패해도 예외가 아니라 0건을 돌려줍니다

### BodyVectorPlan: 계획 3

## service/chat/IssueTools: 모델 호출 도구

| | |
| --- | --- |
| **역할** | 모델이 스스로 골라 호출하는 도구. **등록과 인자 검증 자체가 구현 대상** |
| **확인 방법** | 조회 도구 `*IssueToolsLookupCheckTest`, 검색 도구와 기억 기록 `*IssueToolsMemoryCheckTest`, 요약 도구 `*TopicSummarizerCheckTest` |

일곱 개가 서로 다른 질문에 대응합니다.

| 도구 | 질문 예시 |
| --- | --- |
| `searchIssues` | "코딩 에이전트 한계가 뭐야?", "공식 발표만 찾아줘" (의미 검색, 필터) |
| `countStories` | "AI 관련 이슈가 몇 건이야?" (집계) |
| `listStories` | "AI 쪽 이슈 점수순으로 보여줘" |
| `getStoryDetail` | 특정 스토리의 상세 |
| `getComments` | "방금 두 번째 이슈 댓글 보여줘" |
| `listTopics` | "어떤 기술 분야들이 있어?" |
| `summarizeTopic` | "AI 쪽 논의 흐름 정리해줘" |

**주의 사항**

- 도구 설명이 부실하면 모델이 잘못된 도구를 호출합니다. 설명이 곧 선택 기준입니다
- 반환 타입에 화면용 값(한글 표시 이름 등)을 섞지 마세요. 그대로 모델 컨텍스트로 들어갑니다
- `techField` · `sortBy` · `limit` 은 모두 모델이 채웁니다. 허용 범위를 벗어나거나 비어 있을 수 있으니 검증하세요
- **`techField` · `category` 의 허용값을 `@ToolParam` 설명에 적으세요.** 둘 다 ENUM 이 아니라 TEXT 라
  대소문자까지 정확히 일치해야 걸립니다. 모델이 「하드웨어」나 `hardware` 를 넣으면 예외 없이 0건이 돌아오고,
  그 결과를 근거로 그럴듯한 오답이 만들어집니다. 폴백으로 런타임에 새 값이 생기므로
  「목록에 없으면 `listTopics` 로 확인」도 함께 적습니다
- 빈 문자열은 없는 값으로 바꿔 넘기세요. 그대로 넘기면 「모든 분야」가 아니라 「이름이 빈 분야」를 찾습니다
- 검색·목록 도구는 결과를 대화 기억에 남겨야 후속 질문이 이어집니다. 문구는 `SearchRecord` 가 만들고, `AssistantMessage` 로 기록합니다
- `searchIssues` 의 순서는 Javadoc 에 있습니다: `Query` 구성 → 검색(`SearchService`) → 근거 후처리(`RelevancePostProcessor`) → 근거 합치기 → 사건 방출 → 기록.
  검색과 후처리는 세션 5 에서 Advisor 에 넘겼던 부품을 그대로 부릅니다
- `Query` 의 사용자 원문은 `ToolContext` 에서 읽습니다(`SearchContext.USER_QUESTION`). 검색어 인자는 모델이 다듬은 값입니다

## 문제 해결

해결 방법 대부분은 각 절의 「주의 사항」에 있습니다. 그 밖의 증상은 아래와 같습니다.

| 증상 | 우선 점검 항목 |
| --- | --- |
| 애플리케이션 기동 실패 | Docker 컨테이너 실행 여부 (키가 없어도 기동은 성공) |
| 테스트 실패 | Docker (정상 상태는 전부 통과. 키는 필요 없음) |
| 확인 테스트가 SKIPPED | 적재된 데이터 없음. 데이터 셋업 탭에서 셋업 실행 |
| `.env` 의 키를 고쳤는데 반영되지 않음 | 같은 이름의 환경 변수 `OPENAI_API_KEY` 가 남아 있는지 (환경 변수가 `.env` 보다 우선) |
| 인증 실패 (401) | `.env` 의 값에 따옴표를 붙였는지 |
| 계층 테스트 실패 | 안쪽 계층의 바깥 계층 참조 여부, [02](02-전체-구조.md) 의 「계층」 절 |
| 화면 변화 없음 | 브라우저 새로고침, `psql` 로 DB 행 생성 여부 확인 |
| 스키마 변경 필요 | `docker compose down -v && docker compose up -d` (데이터 삭제됨) |
